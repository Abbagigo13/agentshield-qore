Overview

Why agents need a firewall

An AI agent that can pay is one poisoned invoice away from sending money to an attacker. Prompt injection hides instructions in the text an agent reads, and the agent often cannot tell them from its owner’s. If the agent holds the key, the loss is instant and cannot be undone.

AgentShield removes the key from the agent. The agent only asks. AgentShield decides, and keeps proof.

  1. Check. Nine deterministic rules cover the address, denom, allowlist, per-payment and daily limits, rate and injection patterns. Large payments wait for a person.
  2. Sign. Allowed payments get a hybrid secp256k1 and ML-DSA-87 signature through the QoreChain SDK.
  3. Record. Every decision, including every denial, becomes a signed receipt chained to the one before. Edits are detected, and the proof stays valid after Q-Day.
  4. Let the chain enforce it. In delegated mode the gateway signs with a linked key that QoreChain itself limits. On the testnet, a payment above the on-chain limit was refused by the chain, not by our code.

It is honest about its limits: the allowlist, rate limit, injection scan and approvals live in the gateway only, and the on-chain limit binds a delegate key, not the account owner. The testnet results are in the docs. This site is a browser demo of the real rules and hash chain, not the live gateway.

FAQ

Questions

Does the agent ever hold a key?

No. It submits intents with an agent key that can only ask. The wallet and signing keys stay inside the gateway.

What exactly is post-quantum here?

Transactions are signed with secp256k1 plus ML-DSA-87, and every receipt is signed with ML-DSA-87. The record stays provable even if classical signatures are later broken.

Can the injection scan be bypassed?

Possibly. It is a list of patterns, one layer among several. Limits, the recipient allowlist and human approval still apply when it misses.

What if the gateway itself is hacked?

In delegated mode the gateway holds only a delegate key that QoreChain bounds with an on-chain spending rule. We tested it on the testnet: a 1.5 QOR payment above a 1 QOR limit was refused by the chain. The owner key must stay off the gateway. The allowlist, rate limit, scan and approvals cannot live on-chain, and the on-chain rule does not bind the owner’s own payments.

Can someone delete records from the log?

Edits and deletions in the middle fail verification. Removing the last few records is only detectable if a later on-chain anchor exists, so anchor regularly.

Is this running on mainnet?

No. It targets the QoreChain testnet and defaults to a dry-run mode that signs but never broadcasts.

Is the dashboard live?

Not yet. It runs the same rules and SHA-256 hash chain in your browser. Signatures are added by the real gateway. Connecting the dashboard to the gateway is planned.

How do I connect my agent?

Over HTTP with one function that calls the intents endpoint, or over MCP with the pay and spending_limits tools.
